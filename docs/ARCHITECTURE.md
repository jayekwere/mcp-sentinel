# Architecture

`src/http.ts` owns common request checks and audit visibility. `src/security.ts` verifies signed tokens and returns a server-owned identity. `src/policy.ts` compiles a strict policy and hashes its full canonical content. `src/gateway.ts` owns argument validation, policy decisions, approval state, audit ordering, and detector signals. `src/tools.ts` contains bounded local executors. `src/mcp.ts` adapts the official SDK protocol to that gateway. `src/upstream.ts` is the optional fixed endpoint adapter. `src/store.ts` owns SQLite and HMAC chain storage. The UI is built from local TypeScript and CSS.

A call cannot jump directly from HTTP to an executor. REST and MCP both invoke `Gateway.call`. The identity comes from verified authentication rather than the request body. Tool discovery is filtered by the same policy used for execution. Schema fingerprints are stable canonical digests of local argument schemas.

Approval states are `pending -> approved -> consumed` or `pending -> rejected`. Expired rows are unavailable regardless of their stored status. Approval requests have a five-minute expiry and at most twenty live pending rows per subject. Cleanup removes rows expired for more than a day when a new request arrives. A review can only transition a pending, unexpired row from a different subject in the same tenant. The consumption transaction validates status, actor, tenant, binding, and expiry, changes the row, and appends an audit event atomically. One concurrent caller wins.

After consumption, the gateway durably records execution intent before invoking the tool. A crash between consumption and execution can lose the operation. An upstream timeout can leave its side effect ambiguous. The service deliberately never restores or retries an approval automatically. It offers at-most-one gateway attempt per approval, not exactly-once remote effects. An operator must investigate intent records without completion before authorizing another attempt.

The application records argument digests for execution. Every approval-gated request stores full canonical arguments in its audit detail and approval row so operators can review it even after the recent audit window advances. API and dashboard argument previews stop at 4 KiB and mark truncation. Operators must use the protected local audit database to inspect the complete request before approving a truncated preview. Approval never follows automatically from a token claim or tool description.

Detection is a bounded view of audit evidence. Each group of five new `tool.denied` events by an actor in sixty seconds triggers a burst. Persisted evidence sequences prevent the same denial from contributing to two bursts. `approval.invalid` and `tool.failed` each create a signal. An invalid approval signal can mean expiry, reuse, wrong actor, or argument mismatch; it does not assert malicious intent. Authentication failures have no trusted tenant, are stored under `system`, and are not exposed through a tenant dashboard.

Committed audit events drive persistent detections, optional asynchronous OCSF export, and optional subject suspensions. Both REST and MCP enforce revocations and suspensions at the matched-route authentication hook, including encoded path aliases. Successful auth reload invalidates outstanding approvals, and migration invalidates legacy approvals without stored reviewer arguments.
